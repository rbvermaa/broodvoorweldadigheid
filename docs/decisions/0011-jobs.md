# 0011 Background jobs and the bake day tick

Status: proposed, 2026-11-24

**apalis-postgres, as the spec says.** apalis 1.2 and apalis-postgres 1.2 build on
sqlx 0.9, the version we use, and pass `cargo deny` (MIT; the only new duplicate is the
`toml 0.8` that sqlx's `sqlx-toml` feature pulls in, a warning). They are added with
default features off, so no TLS stack comes along. apalis keeps its tables in its own
`apalis` schema with its own migration table (`apalis._sqlx_migrations`), so our
`migrations.lock` and the add-only rule are untouched. `jobs::setup` runs its migrations;
the server calls it after `db::migrate`. Its migrations create the `hstore` extension,
which ships with the PostgreSQL we build; the database role needs `CREATE` on the database
(hstore is a trusted extension).

apalis-postgres checks its own queries at compile time against `DATABASE_URL` whenever
`SQLX_OFFLINE` is false. `make sqlx-prepare` and the `sqlx-prepare` check therefore run
its migrations on the scratch database first (path from `cargo metadata`), then ours with
`--ignore-missing`. A clean prepare also writes apalis-postgres's query data into our `.sqlx/`, so
those files change when apalis is upgraded. Normal builds stay offline.

**One tick a minute, queued once.** Every server runs `jobs::run`: a Tokio interval that
queues a `BakeDayTick` for the current minute, and an apalis worker. Each server passes
its own worker id: apalis registers workers by id and refuses a second live worker with
the same one. `run` queues the first tick before it starts the worker: an idle apalis
worker fetches again only when its task is woken, at the latest by the 30 s heartbeat, so
a tick pushed while its first fetch is in flight could wait that long. The job carries the
idempotency key `bake-day-tick:<minute UTC>`, so with two servers the second push hits the
unique index and is dropped (`schedule_tick` returns `false`). apalis fetches jobs with
`FOR UPDATE SKIP LOCKED` and retries a failed tick up to 3 times; the next minute's tick
covers anything missed anyway.

**The tick is idempotent on its own.** `jobs::bake_days::tick(conn, clock)` reads the
injected clock once and, in one transaction:

- opens online drafts with `opens_at <= now < cutoff_at`;
- closes open days with `cutoff_at <= now`.

It takes the rows `FOR UPDATE SKIP LOCKED` and then calls `bakedays::days::open` and
`close`, which check the transition again. A row another session holds (a staff edit, a
second tick) is skipped and picked up next minute; a row already moved no longer matches.
It reads the clock once and uses that instant for the transition checks too, so the rows
picked and the checks agree. A refused transition is logged and reported; it does not
block the other days. So it is safe even without the queue, and running it twice changes nothing.

A `FOR UPDATE SKIP LOCKED` query also skips rows held `FOR SHARE`, which checkout takes
(ADR 0008). During a rush at the deadline the close can slip a minute or more, so checkout
must check `cutoff_at` itself and never rely on the stored status alone.

Choices in the same change:

- A draft without `opens_at` is never opened automatically; staff open it by hand or set
  a time. `days::create` leaves `opens_at` empty.
- A draft whose deadline passed without opening stays draft; it already shows closed
  (ADR 0008), and an online draft cannot move to closed.
- Menu publication needs no job: "menu announced" is computed from `menu_publish_at`
  (ADR 0008). The public calendar shows the menu from that time, or once the day has
  opened. A cancelled drop shows no menu. The menu, and the sold-out check, only count active products
  sold online.
- The handler runs against the clock's time, not the queued minute, so a late run still
  does what is due.
- Ticks stay in `apalis.jobs` as done rows, 1,440 a day. A cleanup job that deletes old
  done ticks comes with the other cleanup work.

**Public calendar and iCal (F1a) live in bakedays.** `bakedays::calendar::public_drops`
reads drops for a date range as a display read (no locks, like
`range::availability`) and leaves production-only days out. A planned drop shows its date, pickup slots (location name, address, times), deadline
and charity or "normal sale"; never its menu. Sold out is only computed for open days.
`bakedays::ical::render` writes RFC 5545 by hand: one VEVENT per pickup slot, UID
`pickup-slot-<id>@<domain>`, times in UTC, TEXT escaping, folding at 75 octets without
splitting a UTF-8 character, CRLF endings. Cancelled drops stay in the feed with
`STATUS:CANCELLED` and `SEQUENCE:1`, so subscribed calendars drop them. SEQUENCE is not raised for other changes: that is fine for
a subscribed PUBLISH feed, which clients reload whole, but an imported copy will not
update. Dutch text comes
from `locales/nl/calendar.ftl`. The HTTP routes come in a later slice.
